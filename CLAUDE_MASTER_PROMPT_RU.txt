Ты получаешь существующий рабочий проект **the harry's V19**.

ФАЙЛЫ:
- `index.html` — текущая рабочая версия сайта.
- `PROJECT_CONTEXT_RU.md` — бизнес-контекст, роли, модули и важные ограничения.
- `TEST_MATRIX_RU.md` — обязательный чек-лист тестирования.
- `README_FOR_CLAUDE.md` — правила работы с проектом.

ТВОЯ РОЛЬ:
Ты работаешь одновременно как Senior Product Designer, Senior Frontend Engineer, UX Architect, QA Engineer и Business Systems Analyst.

ГЛАВНАЯ ЗАДАЧА:
Не создавать новый отдельный сайт. Тебе нужно внимательно разобрать существующую V19, сохранить её рабочую бизнес-логику и превратить интерфейс в максимально понятный, удобный, стабильный и визуально профессиональный внутренний продукт для ежедневной работы сотрудников.

==================================================
1. СНАЧАЛА ПРОВЕДИ АУДИТ
==================================================
Перед внесением изменений полностью изучи `index.html`.

Определи:
- структуру страниц;
- sidebar/navigation;
- роли и permissions;
- пользователей;
- филиалы;
- localStorage/state;
- все render-функции;
- все формы;
- все модальные окна;
- все таблицы;
- все графики;
- все Excel-экспорты;
- логику инвентаризации;
- складскую логику;
- продажи;
- финансы;
- зарплаты;
- аренду;
- CEO-раздел;
- техподдержку;
- audit/history.

Найди:
- JS runtime errors;
- undefined functions;
- повторно объявленные функции;
- мёртвый код;
- дублирующиеся UI-блоки;
- неработающие кнопки;
- элементы, которые выглядят кликабельными, но не работают;
- лишние разделы;
- непонятные названия;
- плохую визуальную иерархию;
- места, где один модуль может уронить целую страницу;
- проблемы старых localStorage данных;
- проблемы responsive/mobile;
- таблицы, которые невозможно использовать с телефона;
- модальные окна, выходящие за экран;
- плохо оформленные Excel-выгрузки.

Сначала сформируй короткий AUDIT REPORT с приоритетами:
P0 — ломает работу.
P1 — сильно мешает сотруднику.
P2 — UX/UI улучшение.
P3 — polish.

После аудита СРАЗУ переходи к исправлениям. Не останавливайся только на рекомендациях.

==================================================
2. НЕ ЛОМАТЬ V19
==================================================
Критически важно:
- не переписывать проект с нуля;
- не создавать параллельную CRM/ERP;
- не переводить сейчас на React/Vue/backend;
- не удалять рабочие бизнес-функции;
- не менять смысл ролей;
- не возвращать удалённые разделы без необходимости;
- не менять названия филиалов;
- сохранить существующие demo accounts;
- сохранить существующие данные и бизнес-логику;
- делать резервную копию перед крупными изменениями.

Если функция выглядит плохо — переработай интерфейс, а не удаляй логику.

==================================================
3. СДЕЛАТЬ СИСТЕМУ ПОНЯТНОЙ ДЛЯ ВСЕХ СОТРУДНИКОВ
==================================================
Проверь интерфейс отдельно для каждой роли:

A. Super Admin / IT
B. CEO
C. Управляющий сетью
D. Менеджер Magic City
E. Менеджер High Town
F. Менеджер Cyber Arena
G. Кассир / бариста
H. Повар / сотрудник филиала
I. Кладовщик / заведующий складом
J. Снабженец

Для каждой роли:
1. Войти тестовым аккаунтом.
2. Проверить sidebar.
3. Убедиться, что видны только уместные разделы.
4. Проверить каждую доступную страницу.
5. Проверить все кнопки.
6. Проверить мобильный сценарий.
7. Упростить экран, если роли показывается лишняя информация.

Главный принцип:
Сотрудник должен за 3–5 секунд понимать:
- где он находится;
- что от него требуется;
- что можно нажать;
- какой следующий шаг;
- успешно ли сохранилось действие.

==================================================
4. ПЕРЕРАБОТАТЬ UX/UI БЕЗ СМЕНЫ АРХИТЕКТУРЫ
==================================================
Сделай единый Design System внутри существующего проекта.

Стиль:
- светлый рабочий canvas;
- тёмный sidebar;
- спокойные синие/фиолетовые акценты;
- один визуальный язык для карточек;
- radius примерно 10–14px;
- лёгкие тени;
- аккуратные границы;
- чистая типографика;
- читаемые размеры;
- одинаковые spacing rules;
- минимум визуального шума.

Не использовать:
- огромные кнопки;
- бессмысленные градиенты;
- чрезмерную анимацию;
- слишком много цветов;
- случайные размеры карточек;
- декоративные элементы без функции.

==================================================
5. АНИМАЦИИ
==================================================
Добавь приятные, короткие, функциональные micro-interactions.

Использовать примерно 120–220ms transitions.

Добавить:
- hover для карточек и кнопок;
- мягкое открытие dropdown;
- fade/slide для modal;
- плавное открытие mobile sidebar;
- subtle scale/feedback при нажатии;
- skeleton/loading там, где операция ощущается долгой;
- success check animation после важных сохранений;
- плавную смену фильтров/диаграмм.

Не добавлять:
- тяжёлые 3D-анимации;
- постоянное движение;
- эффекты, мешающие бухгалтерии/инвентаризации;
- анимации длиннее ~300ms без причины.

Учитывать `prefers-reduced-motion`.

==================================================
6. DASHBOARD
==================================================
Dashboard должен отвечать на вопрос: «Что сегодня требует моего внимания?»

Сделай визуальную иерархию:
1. Самое критичное.
2. Основные KPI.
3. Филиалы.
4. Последние действия.

Все KPI должны быть кликабельными и вести в соответствующий раздел/фильтр.

Не перегружать Dashboard десятками равнозначных карточек.

==================================================
7. CEO
==================================================
Это один из самых важных экранов.

CEO не должен видеть мелкую операционную кашу.

Он должен быстро видеть:
- деньги компании;
- долги;
- ожидаемые поступления;
- прибыль;
- доходы/расходы;
- сравнение филиалов;
- зарплаты;
- аренду;
- задолженности поставщикам;
- налоги;
- коммунальные;
- закупки;
- будущие обязательства.

Сделай заметный блок:
**«Предстоящие расходы и одобрения» / «Центр платежей CEO»**.

Каждая запись:
- тип;
- филиал;
- кому;
- краткое основание;
- срок;
- сумма;
- статус;
- хватает ли денег;
- сколько останется после оплаты.

Действия CEO:
- Одобрить;
- Снять одобрение;
- Оплатить;
- Убрать из центра решений без удаления исходной бухгалтерской записи.

Нельзя, чтобы ошибка одного финансового блока ломала всю CEO-страницу.
Каждый блок должен рендериться изолированно и безопасно.

==================================================
11. ИНВЕНТАРИЗАЦИЯ
==================================================
Не менять бизнес-формулу без необходимости.

Сделать интерфейс проще:

- после завершения понятный summary.

- добавлять филиал;

CEO — отдельный стратегический узел.

==================================================
Проверь каждый экспорт отдельно.

Ориентир:
- крупные секционные заголовки;
- объединённые визуальные блоки;
- понятные цвета секций;
- чёткие границы;
- аккуратные суммы;
- разделители тысяч;
- нормальная ширина колонок;
- итоговые строки;
- доход — зелёная логика;
- расход/долг — красная;
- ожидание/частично — жёлтая;
- не делать хаотичную радугу.

Не должно быть `#######` из-за ширины колонок.

Особенно проверить:
- CEO report;
- all finance;
- salaries;
- rent;
- sales;
- audit;
- support.
